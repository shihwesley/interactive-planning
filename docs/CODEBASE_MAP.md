## System Overview

A Claude Code plugin that adds file-based interactive planning with gate-driven user alignment. Two modes: task-based (single plan file, sequential phases) and spec-driven (multi-file specs with dependency DAG, topological sprint assignment). Plans are categorized by type (`feat`, `fix`, `refactor`, `review`, `test`, `polish`, `general`) and stored in `docs/plans/{category}/{name}/` for multi-plan coexistence. Category is auto-detected from user input. Uses `AskUserQuestion` for gates, `TaskCreate`/`TaskUpdate` for progress tracking, and Manus-style file persistence for knowledge retention across sessions.

### Core Skill (Heart of the Plugin)

**Purpose**: Full planning methodology — auto-detection, gates, file creation, execution protocols.
**Entry point**: `skills/interactive-planning/SKILL.md`

| File | Purpose | Tokens |
|------|---------|--------|
| `skills/interactive-planning/SKILL.md` | Planning methodology, gates, execution rules | 4800 |
| `skills/interactive-planning/templates/manifest-template.md` | Spec-driven manifest structure (with category) | 200 |
| `skills/interactive-planning/templates/spec-template.md` | Per-spec file structure (with plan reference) | 260 |

**Phases**:
- Phase 0: Session recovery (scan `docs/plans/*/*/` for multi-plan resume)
- Phase 0.5: Auto-detect plan category + name from user's request
- Phase 1: Interactive requirements (Gates 1–3)
- Phase 2: Create plan directory, tasks, and files under `{PLAN_DIR}`
- Phase 3: Execution with checkpoints

**Gates** (all via AskUserQuestion):
1. Mode + Priority selection (shows auto-detected category/name)
2. Requirements validation (multi-select)
3. Approach (task-based) or Spec Decomposition (spec-driven)
4. Plan validation (show TaskList, approve/adjust)
5. Architecture review (8 dimensions, approve/revise/dig deeper)

**Auto-detection heuristics** (Phase 0.5):
- Keywords map to categories: fix/bug/crash → `fix`, test/coverage → `test`, refactor/migrate → `refactor`, review/audit → `review`, polish/perf/a11y → `polish`, architecture/scaffold → `general`, default → `feat`
- Plan name is slugified from key noun phrases

**Execution protocols**:
- 2-Action Rule: write findings after every 2 search/browse ops
- 3-Strike Protocol: 3 attempts then escalate
- Manual checkpoints: phase completion, unexpected complexity, errors, scope creep

**Dependencies**: Templates, TaskCreate/TaskUpdate/AskUserQuestion tools
**Dependents**: Command router invokes this via Skill tool

## Conventions

- **Categorized plan directories**: All plans live in `docs/plans/{category}/{name}/` — never at project root
- **Auto-detection over extra gates**: Category and name are inferred from user input, not asked
- **PLAN_DIR variable**: All file paths in SKILL.md use `{PLAN_DIR}`, never hardcoded paths
- **File persistence over context**: Research goes in `{PLAN_DIR}/findings.md`, not task descriptions
- **Gates before tasks**: Every decision through AskUserQuestion before creating TaskCreate entries
- **Tasks before code**: All phases materialized as tasks before implementation starts
- **Sub-task naming**: Prefixed with spec name (`data-model: Create schema`) for flat-list readability
- **Two-level task hierarchy** (spec-driven): Parent spec tasks for DAG, sub-tasks for actual work
- **Handoff rule**: Downstream spec's first sub-task blocked by upstream spec's LAST sub-task
- **Legacy compatibility**: Pre-v5 flat-path plans are detected and resumable without migration

## Gotchas

1. **Session recovery scans recursively** — Phase 0 uses `find` to locate all plans under `docs/plans/`
2. **Multiple plans can coexist** — each in its own `{category}/{name}/` directory
3. **Legacy plans are detected but not migrated** — flat-path plans from v4.x work in-place
4. **Reset doesn't clear TaskList** — only removes planning files; tasks remain
5. **planning-advisor is read-only** — only Read, Glob, TaskList tools; cannot modify anything
6. **Inter-spec blocking targets the last sub-task**, not the parent — prevents premature downstream starts
7. **Parent task completion** is derived — only marked `completed` when ALL sub-tasks finish
8. **Sprint assignment is auto-computed** via topological sort but user can override at Gate 4
9. **Open Questions in specs trigger actual checkpoints**, not just documentation
10. **.gitignore excludes planning OUTPUT** (task_plan.md, etc.) — these are test artifacts in the plugin repo, but meaningful in user projects
11. **2-Action Rule matters for multimodal** — screenshots don't persist in context, so immediate capture is critical
12. **`/orchestrate` integration is zero-config** — point it at any `docs/plans/{cat}/{name}/` directory and the ingester finds `manifest.md` or `task_plan.md` automatically
